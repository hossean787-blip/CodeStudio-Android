# ممیزی اجرایی ۱۳ منبع ثبت‌شدهٔ هوش مصنوعی

مبنای فهرست دقیق، `third_party/ai-sources/ai-sources.lock.json` و `AiSourceCatalog.kt` است. این ۱۳ مورد پروژه‌های مستقل اندرویدی/عامل کدنویسی هستند؛ Kilo، NVIDIA NIM، Moonshot/Kimi، Fireworks، Novita و llama.cpp در تنظیمات ارائه‌دهندگان مدل ثبت شده‌اند و عضو این فهرست ۱۳تایی نیستند. AndroidHarness بستر فعلی اپ است؛ Free Claude Code و GPT_API_free دو آرشیو مستقل دیگرند. افزودن همهٔ آنها به عدد ۱۳، منبع یا موتور جدیدی را به‌طور مصنوعی ایجاد می‌کند.

«Gitlink» فقط نشانی Commit سورس بیرونی را ثبت می‌کند؛ سورس‌ها در Build اپ وارد نمی‌شوند. ابزار `python3 scripts/report_13_ai_sources.py` این ۱۳ شناسه، Commitهای ثبت‌شده، خروج از Build و نبود ادعای آزمون اجرا را کنترل و گزارش JSON تولید می‌کند. آزمون کنترل منشأ سورس نیز با `python3 scripts/verify_ai_source_pins.py` انجام می‌شود. این دو آزمون عملکرد عامل‌ها را نمی‌سنجند.

مسیرهای مدل فعلی جداگانه‌اند: Kilo درخواست بی‌کلید محدود و آزموده‌شده دارد؛ llama.cpp از JNI/مدل GGUF محلی استفاده می‌کند؛ OpenAI-compatible برای نام‌هایی از جمله NVIDIA NIM، Moonshot/Kimi، Fireworks و Novita پیکربندی دارد، ولی وجود نام در UI یا پروتکل مشترک اثبات پاسخ واقعی آن سرویس نیست. بدون حساب/کلید مجاز و آزمون مستقل، وضعیت آنها «پیکربندی‌نشده/اجرانشده» باقی می‌ماند. CLIهای Claude/OpenCode/Gemini نیز مسیر opt-in جدا دارند؛ وجود پل اجرا، مجوز سرویس یا نتیجهٔ موفق همهٔ آنها را ثابت نمی‌کند.

برای هر منبع، گام بعدی باید با بررسی کد Commit پین‌شده و مجوز وابستگی‌ها آغاز شود، قابلیت کوچک قابل‌انتقال تعیین شود، سپس تست واحد، دستگاه، امنیت و پاسخ واقعی همان قابلیت ثبت شود. انتقال دسته‌جمعی ۱۳ اپ مستقل به یک APK بدون این مرزها معیار تکمیل را برآورده نمی‌کند.

## بررسی نمونه از کد خود منابع

- `and-code` در Commit `b0be8ad5` واقعاً Runtimeهای OpenCode، Claude Code، Antigravity و Codex، رابط نشست، streaming، تایید ابزار و ویرایش Git دارد. اجرای محلی آن به PRoot و نصب ابزارهای شخص ثالث وابسته است و در README دسترسی به همهٔ فایل‌های گوشی را هم برای حالت «مرور کل دستگاه» شرح می‌دهد. دسترسی سرویس‌های AI و احراز هویت را خود AndCode فراهم نمی‌کند. در صبا استودیو اکنون پل opt-in جدا برای چند CLI وجود دارد، اما هیچ آزمون هم‌ارزی با Runtime AndCode یا آزمون انتقال همهٔ ابزارهای آن انجام نشده است. فعال‌سازی دسترسی همهٔ فایل‌ها نیازمند مجوز صریح و طراحی محدودتر است.
- `droid-harness` در Commit `a3438fdd` یک اپ Flutter همراه با پل Python در Termux دارد؛ اپ به `127.0.0.1:8765` برای ترمینال و به `127.0.0.1:8080` برای `llama-server` وصل می‌شود. کد پل `termux-bridge.py` فرمان و ورودی PTY را از HTTP می‌پذیرد و در کد بررسی‌شده احراز هویت درخواست دیده نمی‌شود؛ localhost روی Android به‌تنهایی مرز امنیتی بین اپ‌ها نیست. این پل نباید به همان صورت در صبا اجرا شود. صبا اجرای مستقل JNI/llama.cpp را روی شبیه‌ساز آزموده است؛ این شاهد اجرای Droid Harness یا GPU Snapdragon نیست.

این دو مورد بررسی نمونهٔ سورس پین‌شده‌اند، نه ممیزی کامل ۱۳ مخزن یا تایید صحت همهٔ ادعاهای README. ۱۱ سورس دیگر هنوز فقط از نظر Gitlink، شناسه و مجوز ثبت‌شده کنترل شده‌اند. برای آنها وضعیت آزمون Runtime همچنان «اجرانشده» است.
